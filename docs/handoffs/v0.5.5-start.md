## Current Google facts to recheck

Google requires separate projects for testing and production tiers. Production web clients should
contain only production origins and no developer-only environment. The app already has a public home
page, Privacy, Terms and the public support address `hello@dustyb.in`.

The `drive.appdata` permission is currently classified as non-sensitive. Google describes the
application data folder as hidden from the user interface and other Drive applications, and accessible
only to the application that created it.

Google's Drive limits page was updated in 2026. At handoff time it states that new projects created
after 2026-05-01 receive 1,000,000 quota units per minute per project, 325,000 per minute per user per
project, and 1 TB daily egress. It also describes a 400,000,000 daily quota-unit billing threshold and
planned later-2026 charging for usage beyond request limits, with advance notice. These are service
facts, not permission to incur a charge. Inspect the actual new-project controls, reduce limits where
Google permits, configure alerts, and record exactly what happens when a limit is reached. Keep
billing unlinked.

## Data-preserving client transition

Do not assume the old and new projects see the same hidden Drive files. Google's public documentation
does not define that cross-project identity boundary precisely enough for this repository to rely on
it. Treat the new project's application-data area as empty until proved otherwise.

The current code calls `initialiseGoogleDriveArticles(fetch, accessToken, localItems)`. If it finds
no remote article snapshot, it creates one from the complete current local list and reads it back for
confirmation. `src/sync/googleDriveArticleSync.test.ts` protects that path. If a remote snapshot does
exist, Drive is loaded as the source of truth. That makes the first device connected to a fresh area
important.

Use this controlled sequence:

1. Confirm one installation contains the complete accepted reading list. Record its exact item count
   and use it as the seed device.
2. Re-run and, if needed, strengthen the focused automated test for seeding an empty Drive area from
   the local list before changing the client.
3. Keep the old OAuth project and client untouched as rollback.
4. Create and safeguard the new project while it remains in **Testing**.
5. Update the application client configuration and public-build audit allowlist, then complete all
   local release gates and deploy through the normal workflow.
6. Update and connect only the seed installation first. Confirm that it reports the exact expected
   item count and that an ordinary addition survives a reconnect.
7. Only after the seed check passes, update and connect the second installation. Confirm it loads the
   same list, then complete one cross-device add and delete round trip.
8. If the seed count or content is wrong, stop. Do not connect the other device or overwrite the old
   project. Restore the old client build and investigate from the preserved local and old-project
   copies.
